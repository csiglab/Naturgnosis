Formulation

What epistemic element type does this instance belong to?

Model. Each transaction follows strict two-phase locking: it acquires locks while running and releases them all only at COMMIT or ROLLBACK.

What is this epistemic instance?

Locks. SELECT takes an S (shared) lock; SELECT FOR UPDATE, UPDATE, DELETE and INSERT take an X (exclusive) lock. Two S locks coexist; an X lock is incompatible with anything else. A transaction that already holds S may upgrade to X if it is the sole holder.

What grounds this reading?

Deadlocks. After every lock wait, a wait-for graph is checked for cycles. If a cycle is found, the transaction that just closed the cycle is chosen as the victim and rolled back — the alert shows the cycle.

Blocking

Blocking. If a requested lock conflicts, the transaction goes waiting and is queued on that row. When the holder releases (commit/rollback), the queue head is re-granted automatically.

Programs & stepping

Programs & stepping. Each transaction holds a multi-statement program (one SQL statement per line). Use Step T1 / Step T2 to advance one statement at a time — you control the interleaving, which is how deadlocks and races are produced. A statement that blocks pauses the program counter (▶); when its lock is later granted (e.g. the other transaction commits), it resumes automatically and the counter advances. Rewind aborts and resets a transaction to its first statement.

Isolation

Isolation you can observe. The “sees” columns show each transaction’s own view: it reads its own pending writes, otherwise the committed value. Notice a writer’s pending value is invisible to the other transaction until COMMIT.

SQL subset

SQL. The text box accepts a small subset: BEGIN, COMMIT, ROLLBACK, SELECT ... WHERE id=N [FOR UPDATE], UPDATE t SET col = V WHERE id=N, UPDATE t SET col = col +/- V WHERE id=N, DELETE FROM t WHERE id=N, INSERT INTO t VALUES (V).
